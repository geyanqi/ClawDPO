我们要做的事情就是使用 agent train dpo

什么叫 agent train dpo：控制我的迭代全流程。自动的帮我执行一些给定的 SOP，并且在适当的时机引入 agent 自己的思考。

Agent 全程接管数据准备，控制启动训练，监控训练，训练完成后自己评测，不达标时自己 loop，达标后退出 loop。

你可以理解为我的构想是这样的。

训练启动方面：其实就是一个训练启动的命令，我这有个认知是说 train model 主要依靠的就是数据。所以其他参数都不改直接干就完了。

数据方面：
从业务角度来说，我们一般会以一个fine-tuned prompt + 基模作为 baseline 发到线上。这时候呢其实每天都会回流很多数据进来。并且这一块吧，其实一般都会先调一个机器评测的的 prompt 。

所以我们就可以去每隔一段时间去拉一下线上的数据，然后走一下机器评测（一个 request file 加一个 curl 命令）。然后我们就可以捞出来一些 不通过机器评测的 badcase 了。

所以你可以假设我们拥有几个机器评测的 prompt + 访问数据库的脚本和对应的表名等等的，便于我们拿到对话数据。然后去设置一些 Codex 的定时任务去拉 sql，然后再去批量的机器评测初步扫数据，过滤出来 badcase，然后我们用 Codex 去精细扫描一下，决定一些有必要去做 DPO 的session，然后再在轮次里挑一些值得训练的轮次，这样我们就可以源源不断的获取训练数据了！

为什么是 DPO：事实上 claw rl是更加吸引人的，但是考虑到 modeltrain model 往往需要比较明确的反馈。直接 train GRPO 本身不够稳定。

但是为了接近 on-policy的感觉，其实我会这么做。

每次 train 之前，我会先把当前待训练的 model 起起来。然后对我们刚才拿到的 prompt 疯狂的去 rollout，每隔 sample rollout 超级大 N 个样本。比如 256 个，以及对应的概率。然后我们去 call 机器评测去得到这些恢复的正确性。然后搭配其正确性和概率值送到 Codex 去得到最值得训练的 2 对样本。

也就是 1 prompt 2 个 training item

你可以认为最好的数据就是，正样本是 概率很大的好回复，负样本是概率很大的差回复，可以是回复的体感差，也可以是正确性有问题。这样我们就可以得到诸多的训练数据。

然后我们就可以把 model 的 training data 指向最新得到的数据去 train dpo了。

一轮结束后我们在一个 training 不可知的评测上再次评测这个模型，看是否有提升。

然后根据测试集上的一些失败，去写规则，写正则，重新去数据库针对性的补充数据，在最新一版本的 DPO 上继续训练。
