# 项目动机

## 项目真正要解决的问题

ClawDPO 的目的不是研究怎么把一个模型继续调大、调复杂，而是把业务模型每天暴露
出来的问题，转化为能够验证、能够复用、能够持续积累的训练数据。

业务基模已经完成了预训练和多轮后训练。它通常不是完全不会回答，而是在一些问题
上答对得不稳定，或者更容易生成一个看似合理但实际错误的回复。此时真正困难的
不是再找一个更大的模型，而是回答下面几个问题：

- 这次错误只是偶然采样，还是模型经常会走的错误路径？
- 模型有没有能力答对，只是正确回复出现得不够稳定？
- 哪些 prompt 值得继续做强化学习，哪些回复适合成为监督数据？
- 一条坏回复究竟从哪里开始走偏？
- 收集到的数据经过训练后，是否真的改善了目标业务模型？

一条线上 badcase 本身回答不了这些问题。它只能证明模型在某一次生成中失败了，
不能证明这条数据具有什么训练价值。

## 为什么必须重新 rollout

ClawDPO 让当前业务模型针对同一个 prompt 生成大量回复，保存每条回复的逐 token
raw logprob 和正确性结果，再对值得精审的候选进行质量判断。项目关注的不是某一
条回复，而是当前模型在这个问题上的实际采样分布。

同一个 prompt 的 rollout 可以暴露几种不同的数据价值：

- 反复 rollout 中同时出现足够数量的正确和错误回复：模型处在“会做但没有学稳”
  的区域，这类 prompt 可以作为后续 GRPO 的候选。
- 正确回复质量高，但出现概率较低：模型已经具备这种能力，只是还不稳定，这类
  回复可以作为完整回复 SFT 的候选。
- 错误回复的相对 likelihood 较高：当前模型更容易生成这类坏回复，它们是 DPO
  rejected 候选和局部分叉研究的重点。
- 两条事实可靠的回复质量差异明确：它们可以形成提升回答质量的偏好关系。

概率、正确性和回复质量必须分开判断。高概率不代表正确，低概率也不代表优质；
只有把三类信号放在一起，才能判断一条回复对当前模型是否真的有训练价值。

## 为什么高概率坏回复最值得研究

普通数据清洗只会给一条回复贴上“好”或“坏”的标签。这个标签可以用于整条回复
的偏好训练，但仍然没有回答模型是在什么位置作出了错误选择。

ClawDPO 使用 Codex-as-Critic 从完整坏回复的错误结果向前回看，定位最早出现的
语义分叉，再映射回业务模型自己的 token。随后从完全相同的 prefix 出发，分别
固定原 token 和一个替代 token，多次生成后续回复，并由另一次 Codex-as-Critic
统一比较两组结果。

只有替代 token 在多次试验中提高了同时通过事实性和任务完成检查的比例、事实性
没有下降，而且整组回复质量更好，这个位置才成为 Verified Branch Point。这样
得到的不再只是“这条回复很差”，而是“在当前采样配置和 Codex 评测口径下，固定
原 token 的这组回复实测更容易失败，固定替代 token 的一组更好”的局部证据。

Verified Branch Point 目前只是经过验证的数据资产，不会被直接写成局部 SFT
样本。如何训练这种局部信号属于后续阶段。

## DPO 和模型训练在项目中的角色

DPO 训练在 ClawDPO 中是一场受控的数据验收实验，不是项目最终追求的对象。

每次实验固定 Base Model、训练配置和 Test Set，用一个冻结的 Dataset Revision
训练 Candidate Model。如果 Candidate 通过既定评测并替代 Best Model，这个结果
同时表示该 Dataset Revision 通过了当前验收。换句话说，在控制其他条件不变时，
模型晋级就是数据版本晋级。

这并不意味着每条 pair 都被单独证明有效，也不意味着这批数据可以直接迁移到任意
其他模型。它表明的是：这批数据按固定训练方案训练后，产出的 Candidate 在固定
Test Set 的既定评测中优于 Base。因此 ClawDPO 长期保存的核心资产不是一个不断
被覆盖的最新模型，而是每次实验的：

```text
Base Model + Dataset Revision + Candidate Model + 完整评测证据
```

即使 Candidate 没有晋级，这次数据、训练过程和失败原因仍然会被保留，继续帮助
判断下一版数据应该改什么。

## 为什么使用 Codex-as-Critic

廉价机器评测适合给大量 rollout 做一致的事实性初筛，但精细数据判断还需要理解
完整上下文、核实外部事实，并区分错误最终写出来的位置和更早的错误决定。

ClawDPO 因此使用运行在 harness 中的 Codex 完成精细判断。Codex 可以读取项目
规则，使用搜索、代码和文档工具，并对判断过程进行结构化约束。它不是一次裸模型
请求，也不是 PPO 中需要训练的 value model，而是数据生产流程中的外部 critic。

Codex-as-Critic 当前承担三类工作：

- 复核候选回复并构造高质量 Preference Pair；
- 定位高概率坏回复最早的语义分叉；
- 同时评测分叉后的两组完整回复，判断替代组是否真正更好。

## 数据价值如何成立

ClawDPO 不用“收集了很多回复”证明数据有价值，而是为数据保存一条完整证据链：

1. 回复来自哪个 Behavior Policy，以及当时使用了什么采样配置；
2. 当前模型生成回复时记录的逐 token raw logprob；
3. 回复是否通过正确性门槛，以及质量优劣的具体原因；
4. chosen 和 rejected 是否都处于当前模型实际会生成的范围；
5. 高概率坏回复能否找到经过反事实 rollout 验证的局部分叉；
6. 最终进入训练的是哪个不可变 Dataset Revision；
7. 该数据版本训练出的 Candidate 是否在固定 Test Set 上晋级。

项目要沉淀的是带有来源、概率、判断理由、反事实结果和训练后验证的数据，而不是
一堆脱离模型分布的好答案和坏答案。

## 目标

- 持续从脱敏业务对话中发现值得重新采样的问题。
- 用当前业务模型的 rollout 判断 prompt 和 response 的不同训练价值。
- 构造事实可靠、方向明确并且处于当前模型分布内的 Preference Pair。
- 把高概率坏回复转化为经过验证的局部分叉证据。
- 冻结并永久保存每一版数据、模型、评测口径和实验结果。
- 用受控训练和固定 Test Set 验收 Dataset Revision，形成可持续的数据循环。

## 非目标

- 不以研究模型结构、扩大模型规模或反复调训练参数为项目目标。
- 不要求数据跨不同规模、不同分布的模型保持同等训练价值。
- v1 不执行完整 GRPO，也不直接训练 Verified Branch Point；它只识别并保存这些
  后续可用的数据。
- 不训练多步 agent trajectory，也不处理工具 action 的副作用。
- 不把 Test Set 原始样本直接加入训练。
- 不负责模型发布、部署或修改线上 serving alias。
- 不把一次模型晋级解释成每条训练样本都获得了单独的因果证明。
- 不把分叉点两组各 16 次的试验解释成统计显著性证明；它只是 v1 的工程筛选门槛。
